# v1.2.9 OCR/PDF repair — configuration, operation, and acceptance

## Scope and security boundary

v1.2.9 repairs same-page mixed PDF extraction while retaining the established architecture: Netlify static React frontend, Render Node API, PostgreSQL, Redis-compatible coordination, private object storage, malware scanning, first-party authentication, protected Hugging Face inference, and the existing durable Knowledge worker.

`server/document-processing.cjs` remains the only shared scanner-gated façade for eligible image/PDF bytes. Chat attachment analysis and Knowledge indexing call it only after their independent owner and clean-scan checks. This release does **not** weaken authentication, ownership, scanner fail-closed behavior, private storage, SSRF controls, artifact access rules, or prompt-injection treatment of extracted text. OCR produces bounded **text extraction**, not visual understanding.

No deployment, secrets, migration, real user document, model request, model replacement, or model-asset operation was performed for this release. The protected model assertion remains `themodelhq/voicechatglm-qwen3-8b` at revision `9f25d05035bfda0de9b36dfc5911ddcdb378f3c8`.

## OCR profiles and strict configuration

`KNOWLEDGE_OCR_PROFILE` is validated centrally by `ocrConfig()`. It accepts exactly `development`, `test`, `staging`, or `production`; absent values are inferred from `NODE_ENV` (`test`, `production`, otherwise `development`). A bad profile makes OCR unavailable. `KNOWLEDGE_OCR_ENABLED` accepts exactly lowercase `true` or `false`; invalid spellings are unavailable, not silently false.

| Profile | Intended configuration | Operational rule |
| --- | --- | --- |
| `development` | `.env.example` and `.env.v129.example` use `KNOWLEDGE_OCR_ENABLED=false`. | Optional OCR is explicitly disabled and reports **disabled by deployment policy**. Local product work must not accidentally fetch a provider or execute an undeclared system OCR binary. |
| `test` | Tests pass a complete, isolated environment with `KNOWLEDGE_OCR_ENABLED=true`, `KNOWLEDGE_OCR_PROVIDER=tesseract_js`, and packaged fixtures. | Real fixture tests invoke the locked package-managed renderer and engine; they do not use a remote service or a mock as proof of OCR. |
| `staging` | Set `KNOWLEDGE_OCR_PROFILE=staging` and enable OCR only after private database, Redis, storage, scanner, model, API, and worker prerequisites are ready. | `/api/readiness` must prove engine/language, PDF rendering, harmless OCR fixtures, and relevant protected-workflow dependencies before acceptance. |
| `production` | `render.yaml` deliberately sets the same bounded local OCR variables, including `KNOWLEDGE_OCR_PROFILE=production`, on the API and the Knowledge worker. | This is an activation blueprint, **not evidence of a deployment**. Production startup rejects invalid OCR configuration and refuses enabled protected file/OCR traffic until database/migrations, Redis, private storage canary, scanner/signatures, protected-model readiness, image OCR smoke recognition, and scanned-PDF smoke recognition succeed. |

The local provider is `tesseract_js`; its language is exactly `eng`, using `tesseract.js@5.1.1` and `@tesseract.js-data/eng@1.0.0`. The optional `remote` provider is accepted only with a credential-free endpoint (HTTPS in production), server-side token, `eng`, and bounded limits. It is not considered ready merely because an endpoint string exists.

Provider, language, boolean, profile, and numeric checks fail closed. Limits include image/request bytes, image pixels, output, concurrency, PDF timeout/pages/render scale/page points/per-page pixels/total pixels/PDF output. The API/worker equal-value check for all OCR limits runs in `npm run validate:config`; it prevents Render drift. Capability/readiness state distinguishes intentional **disabled** from enabled-but-unavailable or malformed configuration, and never exposes credentials.

## Actual readiness semantics

For local OCR, readiness is not a feature flag check:

1. load the package-managed Tesseract runtime and packaged English data;
2. OCR a harmless known-text image fixture;
3. load package-managed `pdfjs-dist@5.4.149` and `@napi-rs/canvas@0.1.100`;
4. render and OCR the harmless scanned-PDF smoke fixture; and
5. for a production file/OCR activation, also require current PostgreSQL migrations, shared rate limiting, private object-store write/read/delete canary, scanner reachability/signatures, and protected model readiness.

A disabled valid configuration reports `disabled`; an enabled malformed/missing configuration reports an actionable unavailable/not-configured state. The worker performs its image and scanned-PDF local probes before polling jobs. It still independently verifies the stored source belongs to the job owner and is in a scanner-success state before reading private bytes.

## PDF behavior repaired in v1.2.9

Each PDF page is parsed with package-managed PDF.js. In addition to native text, PDF.js's operator list is inspected for image paint operators such as `paintImageXObject`. The page outcome is ordered and bounded:

- **`native_text`** — native-only page text is retained without raster OCR.
- **`ocr`** — image-bearing page without usable native text is rendered in memory and OCRed.
- **`mixed`** — a page contains native text and raster evidence. The page is rendered/OCRed even when native text is long enough to have triggered the old shortcut. Native text is retained first, then unique OCR supplement text is appended.
- **ambiguous** — a short native-only page is rendered/OCRed instead of treating a weak text layer as conclusive. Operator-list inspection failure also falls back to an OCR attempt rather than silently omitting potential raster evidence.
- **blank/failed/partial** — no readable text, resource-bound, renderer, or OCR outcomes remain truthful; successful prior pages are retained and the document is `partial` if any page is not complete. Malformed/encrypted/initial parse failures retain their existing safe error codes.

Mixed reconciliation is deliberately bounded and conservative. It removes only exact normalized OCR line copies already present in the native lines; it does not global-deduplicate native lines, so intentional repeats such as invoice/table entries remain. Page number, extraction method, status, and only engine-supplied confidence are retained. The shared extraction also carries ordered provenance (`nativeTextUsed`, `ocrUsed`, `mixedContent`, raster detection/operator evidence and a safe failure code where applicable). It never fabricates a confidence value.

Migration `008_v129_mixed_pdf_page_provenance.sql` expands `knowledge_source_pages` to store `mixed` extraction method and truthful `excluded` status. This also fixes the earlier incompatibility between page-level secret exclusion and the schema constraint. Existing native/ocr values remain valid; the migration is additive at the application-contract level and does not delete source content.

## Fixtures and local regression evidence

All checked-in fixtures are synthetic and contain no user documents or network references.

| Fixture | Proven behavior |
| --- | --- |
| `same-page-native-and-scanned.pdf` | Same page preserves `NATIVE HEADER 2029` and OCRs `SCANNED RECEIPT 47`. |
| `same-page-scanned-table.pdf` | Same page preserves native heading and unique raster table headers/rows. |
| `same-page-scanned-stamp.pdf` | Same page preserves native note and raster `PAID STAMP 2029`. |
| `same-page-overlap.pdf` | OCR/native overlap is removed while native and scanned unique lines remain. |

| retained `scanned-known-text.pdf`, `mixed-known-text.pdf`, `blank-scanned.pdf`, `multi-page-scanned.pdf` | Real scanned, ordered multipage native/OCR, blank/partial, page-limit, smoke-readiness coverage. |

`tests/pdf-ocr-v129-mixed.test.ts` invokes the actual locked OCR engine for the new fixtures. `tests/ocr-config-v129.test.ts` covers disabled versus unavailable status, invalid booleans/provider/language/profile/numbers, and migration contents. Existing scanner-gated chat/Knowledge and redaction coverage remains in the retained v1.2.8 tests.

## Deferred Netlify/Render acceptance checklist

These are required after an authorized staging deployment; none has been claimed complete here.

1. Verify installed Node/dependency lock on both Render API and worker and exact OCR variable parity; preserve the v1.2.8 rollback archive and a verified database backup before applying migration 008.
2. Verify `/api/readiness` reports local English image OCR and scanned-PDF renderer/OCR reachable, then verify `/api/capabilities` reports availability only after all protected dependencies are healthy.
3. From an authenticated browser through Netlify, upload synthetic clean image, scanned PDF, multipage mixed PDF, and same-page native+raster PDF examples. Verify no raw storage key/URL/secret reaches the browser and that native plus unique raster text is cited in page order.
4. Test scanner reject/timeout/unavailable states, owner/cross-owner denial, deleted object, private storage failure, redaction/exclusion, malformed/encrypted/oversize/page/pixel/output limits, cancellation, and worker restart/retry/lease behavior. No bypass or fail-open is acceptable.
5. Capacity-test the package-managed renderer/OCR under the conservative configured worker slot before increasing any bounds or concurrency. Verify logs contain no document bytes, credentials, or extracted secret values.
6. Verify model invocation uses only the retained protected model identifier/revision and that OCR text stays untrusted, delimited evidence. Record only authorized acceptance evidence outside this source archive.

Rollback is application-level: stop accepting new file/OCR work, drain or truthfully fail active jobs, deploy the preserved v1.2.8 archive, and do not drop migration 008 or expose/delete private source objects to roll back. Re-check authentication, owner checks, scanner, readiness, and file-analysis behavior before reopening traffic.
