# v1.3.0 implementation audit — API keys and integrations

**Classification:** source-level implementation and local controlled-test evidence only. This is not evidence of a deployed Render/Netlify service, production database migration, Redis, protected-model inference, object storage, scanner, OCR provider, or staging acceptance.

## Delivered additive surface

| Area | Implemented evidence |
| --- | --- |
| Persistent credentials | `server/db/migrations/009_api_key_management.sql` adds owner-bound `api_keys` and lifecycle-only `api_key_audit_events`. The schema contains no plaintext secret field. It has owner, active lookup, expiry and audit indexes, user foreign keys, uniqueness, nonempty-name, bounded-column and expiry constraints. |
| Credential construction | `server/api-keys.cjs` creates `vcg_<16 base64url id>.<43 base64url random secret>` values from independent CSPRNG bytes. PostgreSQL receives the identifier and HMAC-SHA-256 digest only. Comparison is length-checked and `timingSafeEqual`; bearer parsing is header-only and exact. |
| Ownership/lifecycle | `server/api-key-routes.cjs` derives user ownership exclusively from the first-party session passed by `server/proxy-core.cjs`; create/list/inspect/revoke are session-scoped and state changes require existing CSRF validation. Create is the sole response containing `secret`; list/detail/revoke map metadata only. |
| Revocation/expiration | Credential lookup joins active owner state. `touchApiKeyLastUsed()` conditionally writes only when nonrevoked/nonexpired immediately before protected-model work. It provides a fresh cross-instance PostgreSQL recheck rather than a cached credential result. |
| Public routes | `GET /v1/health` and `POST /v1/chat` are actual Node routes, separate from browser `/api/*` routes. The chat request accepts only bounded text input and a single `chat:write` scope; no client user ID, arbitrary upstream/model, document/file, session, or model credential is accepted. |
| Model boundary | Public chat invokes the same fixed internal `/v1/chat` model path and server-held `VOICECHATGLM_API_KEY` as ordinary protected chat. External bearer values/cookies are not forwarded upstream. The asserted model remains `themodelhq/voicechatglm-qwen3-8b` at revision `9f25d05035bfda0de9b36dfc5911ddcdb378f3c8`. |
| Capacity protection | `server/rate-limit.cjs` adds Redis-compatible shared per-key and per-owner burst/concurrency reservations. These are technical abuse/backpressure safeguards, not billing, credits, subscriptions, or product access tiers. Redis remains mandatory in production. |
| Browser UI | Settings includes responsive API-key list/create/details/revoke controls, expiration/status/last-used metadata, scope display, accessible dialogs and explicit revoke confirmation. The full creation secret is held only in React component state and can be user-copied; it is not persisted in browser/app storage. |
| Contract/docs | `API_INTEGRATION.md`, curl/JavaScript/Python server-side examples and `docs/openapi.yaml` document only implemented `v1` endpoints. `npm run validate:api-contract` checks selected implementation, OpenAPI and documentation anchors. No production URL is claimed. |

## Security review notes

- `PUBLIC_API_ENABLED` is exact lowercase boolean configuration. If enabled, `API_KEY_HASH_SECRET` must be at least 32 characters; production startup reports invalid public-API configuration rather than silently accepting traffic.
- The key identifier has only lookup value. The random secret is not recoverable from the HMAC digest and must not be included in logs, URLs, telemetry, request bodies, browser storage, source control or documentation examples.
- HTTP public responses are `no-store`, `nosniff` and no-referrer and intentionally include **no CORS** headers. Browser `/api` CORS and cookie behavior are unchanged.
- Safe public errors use `{ "error": { "code", "message" } }`; model availability/rejection/timeout is truthful but does not leak upstream credentials or internals.
- This release does not change first-party auth, session cookies, CSRF, scanner gates, private storage, SSRF controls, OCR processing, worker topology or model credentials.

## Schema/test-stack compatibility

Repository active-key creation uses a transaction-scoped PostgreSQL advisory lock (`pg_advisory_xact_lock(hashtext(user_id))`) before counting active owner keys. The disposable pg-mem suite explicitly registers equivalent test functions. Query predicates use a finite `COALESCE(expires_at, NOW() + INTERVAL '100 years')` comparison for pg-mem compatibility while retaining the intended PostgreSQL semantics for unexpired/no-expiration keys. This is local emulator coverage, not a production PostgreSQL migration run.

## Deployment intent and boundaries

`render.yaml` adds a generated `API_KEY_HASH_SECRET`, enables the narrow public API, and lists bounded public limiter values as template intent. `.env.example` leaves it disabled. Neither file was applied to a provider. Before any deployment, an operator must review the release, provision/rotate a real HMAC secret, back up PostgreSQL, apply migration 009 using the normal migration process, verify shared Redis, perform controlled owner/key/revoke/model tests, monitor safe logs, and retain the rollback archive. Do not apply a migration or deploy solely because this source audit exists.

## OCR/profile parity retained

v1.3.0 does not modify the v1.2.9 shared document processor, mixed-page PDF classification, genuine package-managed OCR fixtures, scanner/owner/redaction order, or API/worker OCR configuration parity logic. Development remains explicitly disabled in the example profile; test uses isolated fixtures; the Render template expresses production API/worker parity only.
