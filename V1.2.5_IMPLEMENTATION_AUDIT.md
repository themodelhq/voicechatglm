## Baseline and scope

The v1.2.5 worktree was cleanly extracted from the verified v1.2.4 release archive, SHA-256 `06026932cc395ed0a9fe6bc594300da811700779ddbbc2254d52ed19e29a2ddb`. The immutable baseline copy is `/home/user/baselines/VoiceChatGLM_Frontend_v1.2.4.source.zip` (mode `0444`). See `BASELINE_V125_PROVENANCE.txt`.

The highest-priority confirmed defect was real: `Repository.resubmitConversationUserMessage()` updated the edited user message, soft-deleted subsequent messages and retitled the conversation but did **not** increment `conversations.share_version`. An old preview could therefore pass the old version check after resubmission.

## Implemented repairs

### Share-relevant mutation audit

| Mutation path | Source location | v1.2.5 result |
| --- | --- | --- |
| Create conversation message | `Repository.createConversationMessage` | Locks conversation and increments `share_version` in its transaction. |
| Update message content/status/metadata/role | `Repository.updateConversationMessage` | Locks conversation and increments `share_version` on a matched message. The conservative metadata/status invalidation is safe even when a field is not public. |
| Resubmit user message | `Repository.resubmitConversationUserMessage` | **Fixed:** edited text, trailing soft deletes, title change and `share_version + 1` occur before one commit. |
| Soft delete message | `Repository.softDeleteConversationMessage` | New owner-authorized transactional mutation; increments version. |
| Restore message | `Repository.restoreConversationMessage` | New owner-authorized transactional mutation; increments version. |
| Conversation title/favourite/pin/archive update | `Repository.updateConversation` | Conservatively increments version for all application updates. |
| Conversation delete | `Repository.deleteConversation` | Soft deletes conversation/messages and increments version in one transaction. |
| Direct SQL test fixtures | Test-only fixtures | Not an application route. Production mutations must use the repository boundary. |
| Ownership / access visibility | No application endpoint changes owner or public eligibility | Conversation ownership is immutable through exposed application routes. Public shares always serve immutable snapshots, never live conversation queries. |

The new REST paths are `DELETE /api/conversations/:conversationId/messages/:messageId` and `POST /api/conversations/:conversationId/messages/:messageId/restore`. They require first-party session and CSRF validation through the shared protected route boundary and owner checks in the repository.

### Preview-to-publication integrity

1. `sharePreviewForOwner()` starts a transaction and locks the owner conversation row before counting, reading its requested page, and computing an ordered SHA-256 proof across every eligible candidate message in fixed-size keyset pages.
2. The preview returns `shareVersion` plus `previewDigest`; this digest is not a bearer credential.
3. Share creation requires both values, locks the same conversation row, re-computes the candidate proof, rejects a mismatch with a generic refresh-required conflict, copies the snapshot in 100-message keyset pages, and verifies the copied snapshot proof before committing.
4. The `preview_digest` is retained with the share row by additive migration `006_share_preview_integrity.sql` for auditability. The raw high-entropy bearer token remains hash-only storage.
5. The public endpoint checks the hash-backed token, revocation and expiry inside a transaction on **every** request and serves only snapshot role/text/timestamp data with public rate limiting and cache/referrer/robot protections.

This eliminates the repaired resubmit stale-preview path and adds content proof as defense in depth against same-version/integrity mismatch. A real PostgreSQL concurrency/load acceptance test is still required; pg-mem provides local semantic coverage but is not a substitute for deployed PostgreSQL locking behavior.

### Artifact lifecycle repair

Generated artifacts remain private, server-keyed and owner-authorized. `persistGeneratedArtifact()` deletes a just-written object if metadata creation throws. v1.2.5 fixes the opposite deletion failure: the artifact route now returns success only after the object-store delete succeeds. On a delete outage, it restores the metadata row to `available` when possible and returns `503 ARTIFACT_DELETE_FAILED`; it never reports a completed deletion while leaving bytes behind.

## Intentional non-claims

No credential or authorized endpoint was supplied for live Render/Netlify, Render PostgreSQL, Redis, S3-compatible storage, ClamAV, Brave Search, Hugging Face inference, OCR, embeddings/vector storage, browser rendering or an isolated sandbox worker. v1.2.5 does not install a browser/OCR/vector/sandbox package merely to claim a feature. Conventional HTTP retrieval, lexical knowledge retrieval, deterministic analysis and non-streaming completion retain their existing honest boundaries.
