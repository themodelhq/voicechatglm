## 2. v1.2.6 implementation summary

- Added additive migration `007_advanced_capabilities.sql` for durable private-source jobs, page-level extraction/OCR provenance, and vector lifecycle provenance. It stores no vectors, provider secrets, raw service responses, or public object URLs.
- Changed knowledge indexing API behavior to durable `202 queued` processing. `server/knowledge-worker.cjs` claims leased PostgreSQL jobs; `render.yaml` declares a private Render worker service.
- Added real, fail-closed HTTP adapter contracts in `server/advanced-services.cjs` for private OCR, embeddings/vector gateway, separately hosted isolated execution, and separately hosted JavaScript rendering. There is no local OCR, lexical-as-semantic substitution, Node/child-process code fallback, or static-HTTP-as-browser fallback.
- Added page/OCR metadata, semantic/vector model provenance, hybrid reciprocal-rank fusion, owner filtering before passages are returned, re-index vector deletion gate, delete lifecycle job, and explicit lexical fallback labels.
- Added UI/API workflows for queued knowledge sources, OCR-eligible image types, processing/provenance details, and custom analysis only through an available isolated service.
- Added controlled contract/security fixtures for OCR ordering, embedding/vector owner namespace, sandbox no-network policy request, browser redirect/private-target rejection, and worker native-source processing.

## 5. Security findings and release constraints

1. All added service tokens are server-only variables. No `VITE_*` capability secret is defined; scans passed.
2. Original uploads stay in private object storage. OCR receives only approved private object bytes after the existing upload/scanner path; data is not exposed through public URLs.
3. Vector requests use a server-selected authenticated-owner namespace and result IDs are re-authorized through PostgreSQL before source passages are returned.
4. Browser-rendering responses are rejected unless they attest required private-network denial, per-hop DNS resolution/pinning, and credential non-forwarding; this attestation is not proof of a service that has not been deployed.
5. The sandbox adapter has no local fallback. A child process, VM-like in-process substitute, or unverified container has not been presented as isolation.
6. The new worker's `FOR UPDATE SKIP LOCKED` behavior requires real PostgreSQL acceptance. pg-mem does not implement `SKIP LOCKED`; the local worker processing test uses a controlled repository boundary and is not a concurrency claim.

## 6. Required operator acceptance before enabling advanced service flags

1. Apply migration `007_advanced_capabilities.sql` on staging PostgreSQL and run concurrent worker claim/retry/lease-expiry/re-index/delete tests.
2. Validate private bucket policy/IAM, ClamAV signatures/rejection, retention and owner isolation with the deployed API and worker.
3. Deploy private OCR; run clean-text, scanned, mixed PDF and approved PNG/JPEG/WebP fixtures. Verify page order, provenance, partial/retry behavior and deletion.
4. Deploy an operator-approved embedding model and owner-namespaced vector gateway. Test cross-owner isolation, re-index/delete cleanup, stale vectors, citations and a labeled semantic quality corpus.
5. Deploy a separately hosted sandbox with independently auditable resource/egress/process isolation. Test policy violations and output limits; do not run adversarial probes without owner authorization.
6. Deploy the browser renderer with enforceable egress controls. Test redirect chains, DNS rebinding/private ranges, malformed responses, timeouts and public client-rendered pages under explicit authorization.
7. Only mark a capability `tested`/available in release evidence after the relevant controlled deployed acceptance is recorded.
